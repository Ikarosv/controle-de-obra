## 4. Governance Protocol & Hard Gate Pipeline

### 4.1 Sequência Obrigatória de Quatro Fases
```
[1. Planejamento] ──────► [2. Implementação + Testes] ──────► [3. Revisão Arquitetural] ──────► [4. Auditoria de Segurança]
(tech-lead-architect)     (backend + frontend + QA)            (tech-lead-architect)            (ciso-security-lead)
                                                                       │                                │
                                                                       ▼                                ▼
                                                            APPROVED_BY_TECH_LEAD             APPROVED_BY_SECURITY
                                                          (ou CHANGES_REQUESTED)               (ou REJECTED_BY_SECURITY)
```

1. **Fase 1 — Planejamento Arquitetural (`tech-lead-architect`)**:
   - Decomposição da demanda em especificação técnica, diagrama de entidades, contratos de Server Action e componentes UI.
   - Emissão do plano aprovado para implementação.
2. **Fase 2 — Implementação (`senior-backend-eng` / `senior-frontend-eng`) + Testes (`senior-qa-sdet`)**:
   - Engenheiros desenvolvem a funcionalidade conforme arquitetura e padrões técnicos.
   - O SDET (`senior-qa-sdet`) executa testes automatizados, valida edge cases financeiros e RBAC.
   - Se tudo passar, emite `APPROVED_BY_QA`. Se falhar, emite `QA_BLOCKED` e devolve aos engenheiros.
3. **Fase 3 — Revisão Arquitetural (`tech-lead-architect`)**:
   - Análise de Clean Architecture, separação Server/Client, qualidade TypeScript e ausência de regressões.
   - Emite `APPROVED_BY_TECH_LEAD` para prosseguir, ou `CHANGES_REQUESTED_BY_TECH_LEAD` para ajustes.
4. **Fase 4 — Auditoria Final de Segurança com Poder de Veto (`ciso-security-lead`)**:
   - Auditoria impeditiva de OWASP Top 10, NextAuth v5, Server Actions RBAC e dados sensíveis.
   - Emite `APPROVED_BY_SECURITY` para autorizar a conclusão, ou exerce o poder de veto com `REJECTED_BY_SECURITY`.
